Термины и определения

1.1. Авторизованный адрес электронной почты – адреса электронной почты
Оператора, созданные на доменном имени Оператора, а также адрес
электронной почты Пользователя, указанный им в качестве авторизованного
адреса электронной почты при заключении с Оператором договора на
условиях Пользовательского соглашения. Вся переписка, обмен документами
по Авторизованным адресам электронной почты имеют юридическую силу и
считаются подписанными простой электронной подписью. Такие переписка,
обмен документами являются юридически значимыми, как если бы
осуществлялись на бумажных носителях с подписью уполномоченных лиц.

1.2. Авторизованный номер – номер(а) мобильного телефона Пользователя,
указанный(ые) им для целей заключения с

Оператором договора на условиях Пользовательского соглашения. Данные,
полученные с/ отправленные на указанный(ые) номер(а) телефона, считаются
безусловно направленными/ полученными Пользователем. В случае смены
Авторизованного номера Пользователь должен незамедлительно сообщить об
этом Оператору.

1.3. Аккаунт — учетная запись Пользователя, создаваемая в момент
регистрации на Сервисе, позволяющая Пользователю воспользоваться
функциями Личного кабинета. Действия, совершаемые через Аккаунт после
Аутентификации, признаются юридически значимыми и совершенными
конкретным Пользователем.

1.4. Аутентификация — процедура проверки принадлежности лицу прав
доступа к Аккаунту. Аутентификация считается пройденной в случае
соответствия предъявленных Авторизованного номера и Пароля. Без успешной
Аутентификации доступ к Сервису не предоставляется.

1.5. Договор на оказание Услуг – договор оказания услуг или договор
выполнения работ, заключаемый между Пользователем и Оператором, по
которому Оператор обязуется выполнить определенные обязательства
(оказать услуги, выполнить работы), а Пользователь обязуется оплатить
их.

1.11. Номинальный счет – счет, открытый Оператору в Банке () для
совершения Операций (за счет отдельного Заказчика). Бенефициаром по
Номинальному счету выступает Заказчик. Заказчик обязуется предоставлять
Оператору документы и информацию, необходимые для
открытия/обслуживания/закрытия Номинального счета, в том числе - по
запросам Банка. Оператор не несет ответственности за действия Банка, в
том числе - за отказ Банка проводить операции по Номинальному счету.

1.12. Оператор – Общество с ограниченной ответственностью «-» . Оператор
на условиях Пользовательского соглашения предоставляет Пользователям
Сервис.

1.13. Операция – операция с денежными средствами, права на которые
принадлежат Пользователю, совершаемая Банком по распоряжению
Пользователя посредством Сервиса. Информация об Операциях отображается
на Сервисе.

1.14. Пароль — секретный четырехзначный Код, который направляется в
СМС-сообщении на Авторизованный номер по запросу Пользователя на
Аутентификацию/ регистрацию на Сервисе.

1.15. Пользователь (Пользователи) – юридическое лицо, физическое лицо
или индивидуальный предприниматель, акцептовавший настоящее
Пользовательское соглашение.

1.16. Пользовательское соглашение – пользовательское соглашение между
пользователем и Оператором.

Назначение

Сервис предназначен для обеспечения информационно-технологического
обмена участников системы, представляющее собой совокупность модулей,
работающих как единое целое, так и по отдельности, (мобильное и вэб
приложение, API), предназначенное для дистанционного обслуживания
клиентов, виртуализации счетов и расчетов, управления счетом и доступа к
сторонним финансовым и нефинансовым услугам.

Сервис решает задачи:

- Обмен данными между системами (банк, процессинг, клиентское
  приложение, учетные системы)

- Взаимодействие с пользователем (через пользовательский интерфейс)

- Учета, статистика, обработка данных по операциям

[]

Пользователи:

- Банки

- Компании

- Частные пользователи

- Экосистемы

Область применения:

Для банков:

- Предоставление финансовых и нефинансовых услуг пользователям

- Оптимизация взаимодействия с пользователями и повышение эффективности
  бизнес процессов, особенно в части обслуживания торговых экосистем и
  маркетплейсов

- Переформатирование маршрутов международных платежей

- Создание цифровых экосистем, бесшовная интеграция и взаимодействие
  между клиентами и участниками экосистемы

- Управление данными

Для пользователей:

- Упрощение взаимодействия с банковскими и финансовыми сервисами

- Организация бизнес процессов по работе с финансами, товарными сделками

- Получение дополнительных услуг

        стоимости транзакции;

      - среда для структурирования, конструирования, учета цен, тарифов,
        опций тарифов;

      - набор и описание сущностей для формирования параметров услуг.

Маркетплейс товаров и услуг

- Предназначен для позиционирования сторонних и партнерских поставщиков
  товаров и услуг

- Ведет учет сторонних покупок в программе лояльности, стимулирование
  кросс потребления;

- Регистрирует товары и услуги;

- Формирует список покупок пассажира (корзину товаров);

- Для покупки товаров и услуг пользователем с виртуального кошелька
  требуется регистрация этих товаров и продавцов в системе для
  отслеживания транзакций и дальнейших расчетов.

Сервис управления платежами

Управление конечными взаиморасчетами между участниками согласно
условиями договоров.

Поставка данных для формирования финансовой и управленческой отчетности,
в том числе, для сверки между участниками

Обеспечение взаимодействия с финансовыми инструментами кредитных
организаций, используя открытое API для работы с виртуальными и другими
картами

Система автоматизированного учета финансовых операций предназначена для
технологического обеспечения расчетов между пользователями системы и
внешними контрагентами. Основные функции системы:

- Формирование заказов

- Формирование счетов - инвойсы

- Управление транзакциями

- Формирование запросов

- Фиксация событий

- Управление финансовыми счетами, балансами

- Управление расчетами

- Учет разных типов операций (конто): пополнение, оплата с кошелька,
  оплата с карты, оплата купоном и др.

- Осуществляет снятие комиссий, кэшбэков при транзакциях

- Ведет историю транзакций и выдает данные о транзакциях;

Функционал системы связан с бизнес-процессами и отражает их взаимосвязь.

Базовый процесс включает:

- Заказ / Запрос

- Формирование счета

- Событие

- Расчет (вычисление) / интеграционное взаимодействие

Заказы

Расчет цены в рамках оказания услуги пользователю, при успешном
выполнении процесса, на следующем шаге формирует Заказ, содержащий
данные расчета и примененного тарифного плана. В заказе присутствуют все
возможные варианты расчета цены по тарифному плану.

Заказ является одновременно платежным поручением и основанием для Счета
– инвойса.

Работа с Заказами включает создание (POST), редактирование (PUT),
удаление (DELETE) и просмотр (GET). Удаление возможно как отдельного
Заказа, так и нескольких для одного Пользователя, а также общее удаление
всех Заказов в системе.

Заказ состоит из атрибутов:

- идентификатор пользователя userId,

- идентификатор Заказа orderId,

- дата и время (опционально, по умолчанию системные) dt,

- статус Заказа согласно справочнику status:

  - "created": 10,

  - "accepted": 11,

  - "commited": 12,

  - "invoiced": 13,

  - "rejected": 20

- Тип Заказа (например, транспортная услуга) orderType,

- Дополнительные опциональные данные (валюта и сумма Заказа, учетная
  единица, идентификатор тарифного плана)

Счета - инвойсы

При акцепте Заказа пользователем, согласно базовому процессу, создается
счет – инвойс для проведения оплаты. Работа со счетами - инвойсами
включает создание (POST), редактирование (PUT), удаление (DELETE) и
просмотр (GET). Аналогично Заказам возможны удаление всех счетов, счетов
одного пользователя и отдельного счета.

Для счета – инвойса предусмотрен функционал проведения оплаты и создания
учетных транзакций и функционал непосредственной оплаты.

Отдельная сущность системы – Купоны, обеспечивает учет эмиссии купонов и
их погашение.

[Изображение выглядит как текст Автоматически созданное описание]Для
создания счета – инвойса необходимо указать идентификаторы пользователя
и Заказа, уникальный paymentCode платежный код варианта (из Заказа) в
случае выбора пользователем, а также режим оплаты paymentMode
("transportWallet": 10, "bankCard": 11, "seasonTicket": 12, "coupon":
13, "token": 14)

Предусмотрены следующие статусы для счета – инвойса:

- "canceled": 0,

- "paid": 1,

- "approved": 2,

- "waitingOnApproval": 3,

- "reversed": 4,

- "scheduled": 5,

- "void": 6,

- "sent": 7,

- "overdue": 8,

- "partialPaid": 9

Инвойс выполняется с единственным параметром – идентификатором инвойса.

Особенности учета

В системе предусмотрен учет транзакций по индивидуальным финансовым
счетам.

Счет обладает атрибутами: дата и время создания dt, дата закрытия счета
dt_end, идентификатор пользователя userId и счета acountId, способ
оплаты conto, валюта assetCode, тип счета accountType

Валюта в системе кодифицирована unit для удобства поиска. Каждому
значению assetCode соответствует цифровой код unit.

Счета объединены Планом счетов, который содержит перечень уникальных
аналитических признаков conto. Для случая расширения необходимо добавить
новый аналитический признак в действующий План счетов.

Счета можно создавать по отдельности и для одного пользователя списком.

Предусмотрен функционал синхронизации остатков по счету с внешней
системой. Транзакции создаются согласно внутренней логике учета по
индивидуальным счетам пользователей в корреспонденции со счетами
системного пользователя в целях оптимизации учета.

Данные по транзакциям агрегируются на уровне баланса. Реализован
функционал расчета баланса на заданную дату (с даты по дату)
balance/show, синхронизации баланса со внешней системой посредством
отправки данных баланса balance/send, создания баланса в системе
посредством приема данных от внешней системы balance/create

Запросы и События

Расчеты между пользователями осуществляются посредством создания и
обработки запросов. Данный функционал поддерживает интеграции с внешними
системами, отправку и прием платежных поручений, согласование и
проведение операций.

Обработка запросов осуществляется через изменение статуса.

В события заносятся системные сообщения, сведения об ошибках и
нарушениях в данных.

Сервис статистики и мониторинга

Система предназначена для хранения и вывода данных об операциях
пользователей

Получение клиентом данных по операциям должно содержать настройку
системы фильтров для вывода истории операций

История операций должна содержать все данные об операции, включая:

- Дату и время

- Сумму операции

- Контрагентов

- Тип операции

- Данные платежного поручения

- Тарифный план

- Назначение

- Тип счетов

- Валюту операции

Сервис должен отображать данные по операциям в разрезе параметров
операций

Сервис должен генерировать отчеты и передавать данные по запросу
посредством API

Сервисы финансовых инструментов

Сервис финансовых инструментов предназначен для управление сценариями
платежей и расчетов пользователей относительно контрактов, покупки
товаров и услуг

Финансовые инструменты включают:

- Использование внутренней ликвидности участников: внутренние
  взаимозачеты и использование ликвидности внутри цепочки контрагентов

- Автоматизация исполнения сделок: настройка действий по организации
  транзакций при совершении условий договоров или наступления событий
  (расписания, реестры выплат, настройка условий)

- Автоматизация комиссий: распределение комиссий и платежей контрагентам
  при наступлении условий, с предварительным холдированием средств и др.

Модуль управления договорами

Предназначен для генерации и управления договорами пользователей

Договор должен содержать следующие данные:

- Контрагентов

- Дату заключения

- Даты этапов и окончания

- Стоимость договора, стоимость этапов

- Статус

- Текущие выплаты

Сервис должен обеспечивать следующий функционал в части организации
платежей:

- Создание нового договора с параметрами

- Генерацию счета и цифрового инвойса по договору

- отслеживание операций по договору

требования к программному обеспечению

  Программное обеспечение представляет собой серверный код, который
  реализует API для различных операций.

  Языки программирования JavaScript и Typescript на платформе Nodejs
  (v.14 или выше)

  В качестве серверных операционных систем могут использоваться Ubuntu
  версии 20 и выше.

  В качестве СУБД используется MongoDB версии 4.2 и выше, а также
  PostgreSQL версии 12 и выше.

  сервисы должны разрабатываться с учётом микросервисной архитектуры и
  предусматривать работу в окружении кубернетес.

  сервисы должны разворачиваться соответственно процессам CI/CD

  при передаче сервисов все необходимые компоненты должны быть загружены
  на Git и проведён цикл развёртывания сервисов с этого Git в облаке.

  весь трафик между сервисом и ядром должен быть зашифрован с
  использованием протоколов TLS 1.2/1.3

  API между сервисом и ядром должен быть согласован Исполнителем и
  Заказчиком, испытан и отлажен в процессе разработки. Эти работы должны
  производиться на протяжении всего этапа, а не в его завершение.

  вместе с передачей сервиса должна предоставляться техническая
  документация по составу, разворачиванию, использованию сервиса и
  возможности модификации сервиса в будущем.
